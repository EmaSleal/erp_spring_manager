Sí. Para emitir comprobantes electrónicos hacia Hacienda (DGT) y gestionar la respuesta su app debe cubrir, como mínimo, cumplimiento tributario + integración técnica + resguardo.

1) Lo que necesita a nivel “negocio/tributario” (prerrequisitos)

Estar inscrito en el RUT y tener acceso a ATV (Administración Tributaria Virtual). Esto es base para operar como emisor/receptor electrónico y para credenciales del API.

Soportar versión 4.4: Hacienda definió uso voluntario desde 1 de abril 2025 y obligatorio desde 1 de setiembre 2025, con convivencia 4.3/4.4 en ese rango.

Certificado para firmar: el XML que envía debe ir firmado digitalmente (ver punto técnico).

2) Lo que necesita a nivel técnico (integración directa con Hacienda)
A. Generar el XML v4.4

Su sistema debe construir el XML conforme “Anexos y Estructuras v4.4” (campos, catálogos, clave, consecutivo, impuestos, CAByS, etc.).

B. Firmar el XML (obligatorio)

En el API de Hacienda, el campo comprobanteXml se envía como XML firmado con XAdES-EPES, convertido a bytes y codificado Base64 (UTF-8).

C. Autenticación (token)

Hacienda expone un API REST protegido con OpenID Connect sobre OAuth2; usted obtiene token en el IdP y lo manda como Authorization: bearer <token>.

El token expira rápido (5 minutos); su app debe renovarlo automáticamente.

La contraseña para el API se genera desde ATV (menú de Comprobantes Electrónicos) y llega al buzón.

D. Envío y consulta de estado

Flujo típico:

POST /recepcion con JSON (incluye clave, fecha, emisor, opcional receptor, y comprobanteXml base64).

Recibe HTTP 201: “recibido, pendiente validación”.

Luego obtiene el resultado:

Polling: GET /recepcion/{clave} (estado/resultado).

Callback (recomendado): usted envía callbackUrl y Hacienda le “empuja” la respuesta por POST cuando termine la validación.

E. Ambientes: pruebas y producción

Hacienda publica producción y sandbox para integrar y validar su implementación (recomendación: CI/CD contra sandbox).

3) Gestión de respuesta (lo que su sistema debe “operar” sí o sí)

Estados y trazabilidad por clave: trate la clave como su idempotency key (si reintenta, evite duplicados; Hacienda incluso devuelve errores si ya fue recibido).

Persistencia de evidencias: almacene como mínimo:

XML emitido (firmado)

JSON enviado al API

respuesta/acuse de Hacienda (y su estado)

bitácora de intentos/errores por documento

Reintentos y cola: su “motor de envío” debería correr desacoplado (cola/worker), con:

reintentos con backoff

circuit breaker si IdP/API cae

rate-limit handling (Hacienda expone headers de rate limit).

4) Resguardo legal y continuidad operativa

Conservación: el reglamento exige almacenar comprobantes (y asociados) por 5 años.

Si usa el gratuito TicoFactura, tenga claro que solo almacena ~2 meses; igual debe respaldar por su cuenta.

Contingencia: el reglamento exige planes de continuidad; si su sistema no puede emitir por fuerza mayor, existen reglas de contingencia que usted debe contemplar operativamente.

5) Endpoints (para que su equipo lo aterrice rápido)

Póngalo tal cual en su configuración (separando sandbox/prod) y versionándolo por ambiente.

2) Flujo operativo recomendado (MVP “manual”, pero controlado)
Paso 1 — Generar numeración y clave

Consecutivo (20 dígitos): SSS TTTTT TT NNNNNNNNNN

Sucursal (3), terminal (5), tipo comprobante (2), consecutivo (10)

Para factura electrónica, tipo = 01

Clave (50 dígitos): incluye 506 + fecha + cédula emisor (12) + consecutivo (20) + situación (1) + seguridad (8)

Situación: 1 normal, 2 contingencia, 3 sin internet

La cédula del emisor para la clave debe ir “padded” a 12 según el tipo

Paso 2 — Construir XML v4.4 (FacturaElectronica)

Debe ajustarse al schema v4.4 (Factura Electrónica).

Paso 3 — Firmar XML (XAdES-EPES)

Firma obligatoria (XAdES-EPES).

Paso 4 — Enviar a Hacienda (POST)

Endpoint de recepción (prod): https://api.comprobanteselectronicos.go.cr/recepcion/v1/recepcion

El JSON incluye (mínimo):

clave (50)

fecha formato RFC3339 yyyy-MM-dd'T'HH:mm:ssZ

emisor.tipoIdentificacion + emisor.numeroIdentificacion

comprobanteXml (XML firmado en Base64 UTF-8)

opcional callbackUrl

Si lo recibe bien, devuelve 201 y un Location para consultar estado.

Paso 5 — Consultar estado (GET) o recibir callback

GET: /recepcion/{clave}

Callback: Hacienda le hace POST con el mismo JSON que daría el GET; reintenta 3 veces si no recibe 200.
